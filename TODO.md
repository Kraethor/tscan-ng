# tscan-ng code review TODO

Local worklist from the 2026-09-29 review. Code was **not** modified by the review; only docstrings, comments and docs were. Each item says what to change and why.

**Provenance / trust.** Findings come from three review passes (core, detectors, scripts+deploy). "Reproduced" = the reviewer ran a script against the real function or observed the live host read-only. "Inference" = read from code, not exercised. Nobody has re-verified these independently yet, so reproduce before fixing. Line numbers are approximate (docstring edits shifted them); function names are the stable anchor.

**IDs.** Flat, stable `#N`. A closed item's number retires with it; do not renumber. Severity: HIGH = wrong/missed credentials or silent loss of alerting; MED = correctness, security or reliability gap with a realistic trigger; LOW = polish, edge cases, cleanup.

Working files behind this list (gitignored, may be stale): `.claude/findings_core.md`, `.claude/findings_detectors.md`, `.claude/findings_scripts.md`.

## HIGH

- [x] **#1 postgres: password missed whenever the StartupMessage contains a `p`** (reproduced). `postgres.py` `_find_password_message` does `find(b"p")`, reads the next 4 bytes as a length, and on "length > buffered" returns `(None, None)` ("wait for more data") instead of trying the next `p`. The StartupMessage is never consumed and always contains `p` ("postgres", "application_name", "psql"); the following ASCII decodes to a ~1.8e9 length. Repro: startup `user=postgres database=postgres application_name=psql` gives `(None, None)`; `user=bob` alone finds the password. *Change:* consume the StartupMessage (and any SSLRequest) once parsed so the buffer starts on a message boundary; `continue` to the next `p` on an implausible length, with a length cap. *Why:* the detector misses most real logins. **DONE 2026-09-30:** `_find_password_message` now starts after the StartupMessage/SSLRequest (`_startup_end`) and skips a candidate `p` whose length exceeds the scan window instead of waiting on it. Regression tests in `tests/test_detectors.py`.
- [x] **#2 http_basic: stale 401 challenge pairs with the credentialed retry** (reproduced). `_parse_response` takes the first status line in `server_buf`; responses to requests without `Authorization` are never consumed. Browser flow (no-auth request, 401, retry with credentials) resolves the retry immediately as `failed/401`, which Discord suppresses. *Change:* record a `server_buf` offset floor when the request is seen, or count requests against responses; `run.py` `_try_resolve` needs the same change. *Why:* the standard browser Basic-auth flow is reported as a failure. **DONE 2026-09-30:** every request block is numbered (`Session.http_req_seen`) and a credentialed request is paired with the status line at its own position via `http_basic.take_response` (also used by `run.py`); the 401 for a credential-less request is skipped. `take_response` also shifts pending floors, so #13 is fixed for http. `_parse_response` removed. Limits: assumes in-order responses and no `100 Continue`. Regression tests added. **Live-verified 2026-09-30 via the SPAN port (httpbin.org):** `curl --anyauth` (no-auth request, 401, retry on the same keep-alive connection) reports `success`/200 (old code: `failed`/401); wrong password reports `failed`/401; direct credentialed request reports `success`/200. #1 and #3 are unit-tested only (no live Postgres/IRC target used).
- [x] **#3 irc: `_IDENTIFY_RE` `\s+` crosses CRLF** (reproduced). `PRIVMSG NickServ :IDENTIFY hunter2\r\nJOIN #chan\r\n` yields nick=`hunter2`, password=`JOIN`. *Change:* `[ \t]+`, as imap's LOGIN regex does. *Why:* wrong credentials get reported when commands are pipelined. **DONE 2026-09-30:** `_IDENTIFY_RE` now uses `[ \t]+` separators instead of `\s+`. Regression tests added.
- [x] **#4 healthcheck fails silently when the capture NIC disappears** (code-path only; NIC not unplugged). `scripts/pipeline_healthcheck.py` ~L138 builds `Config()`, which validates `capture.iface` against `/sys/class/net`. If the USB NIC vanishes (the documented main failure), it raises `ValueError` before `is-active` is checked: exit 1, no external DOWN alert. *Change:* read the webhook without full validation, check `is-active` first, and alert on config-load failure. *Why:* the watchdog dies exactly when it is needed. **DONE 2026-09-30:** `Config` gained `validate=` (default True, so the pipeline is unchanged); the healthcheck loads the webhook via `Config(validate=False)` in `_load_webhook()` and treats an unreadable config as an empty webhook, so the systemctl check and marker logic always run. Tests in `tests/test_healthcheck.py` (real `Config` with a nonexistent NIC). Not exercised live: unplugging the capture NIC was not attempted.

## MED: security / deployment

- [~] **#5 Live config holds the Discord webhook** (PARTLY DONE 2026-09-30). Was mode 0664 `thoward:thoward`; now 0640 `thoward:tscan` via `chgrp`/`chmod` (no sudo needed), so the service reads it through the group and other users cannot. Confirmed by a service restart 2026-09-30: the service started and read the config under 0640 `thoward:tscan`. REBUILD says `tscan:tscan` 640; `thoward:tscan` 640 is the current state. *Still open:* the webhook URL may have appeared in tool output during the review sessions, so consider rotating it (owner's call).
- [ ] **#6 Credential logs are world-readable** (reproduced). `/var/log/tscan` is 775; `results.jsonl` and rotated `.gz` are 644 and hold cleartext credentials. REBUILD said 750; the unit has no `UMask=`. *Change:* pick a policy: 750 dir + `UMask=0027` + a group for the viewers, or document world-read as intended. Rotated files inherit 644 (see #47). *Why:* harvested passwords should not be readable by every account on ser8.
- [ ] **#7 Service hardening is partial** (measured: `systemd-analyze security` 7.1 MEDIUM). Missing on `tscan-pipeline.service`: `NoNewPrivileges`, `ProtectSystem=strict` + `ReadWritePaths=/var/log/tscan`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`, `ProtectKernel*`, `RestrictAddressFamilies` (AF_PACKET INET INET6 UNIX NETLINK), `LockPersonality`, `UMask`. The service user owns `/opt/tscan` (775), so a compromise can rewrite code that runs at next restart: add `ReadOnlyPaths=/opt/tscan`. Inference: `CAP_NET_ADMIN` may be droppable if `rmem_max` is raised; `MemoryDenyWriteExecute` likely breaks ctypes. *Why:* this process parses hostile network input as a privileged user.
- [ ] **#8 `watch.py` prints attacker-controlled fields raw** (read-only analysis, not exploited). `creds`, `host`, `uri`, `user` come from network traffic; JSON-decoded ESC bytes reach the operator's terminal (escape injection). *Change:* escape control characters in `_format`. *Why:* the viewer runs on the operator's terminal and the input is hostile by definition.
- [x] **#9 SNMP community string is sent to Discord** (reading of code). `discord.py` `_send_finding` uses `creds.split(":")[0]`; SNMP creds is a bare community with no colon, so the whole string goes out (intended output is probably just a username). *Change:* special-case SNMP or make the field mapping per detector. *Why:* leaks a credential to a third-party service where other protocols send only a username. **DONE 2026-09-30:** `discord._send_finding` withholds `creds` for types in `_NO_USERNAME_TYPES` (`snmp_creds`); the alert shows `(none - secret withheld)`. Full value stays in the JSONL. Only SNMP had a colon-less `creds`. Tests in `tests/test_discord.py`.

## MED: correctness / reliability

- [ ] **#10 Cooldown is claimed too early and keyed without outcome.** `pipeline.py` `_emit`: key is (dst, dport, creds). A first `failed`/`no_response` finding consumes the 30-minute window, so a later `success` with the same creds is dropped from both sinks. A `sink.write` exception also burns the window. *Change:* include outcome in the key, or claim only after a successful write. *Why:* the success is the finding that matters most.
- [ ] **#11 Cooldown marker files are never pruned.** One tmpfs file per unique key under `_FINDING_COOLDOWN_DIR`; a password-spraying scanner fills it. *Change:* sweep old markers from `_maybe_run_periodic`. Related: #41.
- [ ] **#12 `Session._SERVER_PORTS` is hardcoded** (`session.py`; reviewers agree). Omits 161, 389, 445, 139, 3268, 5432, 6379, 66xx, 3128, 8080; includes 22 and 443, which no detector uses. If the first packet seen for a flow is server-to-client (capture starts mid-flow) client/server buffers are swapped for the session's life and detectors find nothing; SNMP with a fixed poller port is worst. *Change:* derive the set from the configured detector ports. *Why:* silent false negatives.
- [ ] **#13 Immediate-resolve paths do not call `session.shift_pending_floors()`** (`run.py` does). Affects ftp, pop3, smtp, http, redis, ldap, smb, snmp, irc, postgres. After such a delete another pending finding's `server_buf_floor` is stale. *Change:* add a `Session.consume_server(n)` helper that deletes and shifts floors, and use it everywhere. Partly inference: audit each detector.
- [ ] **#14 Positional response correlation pairs unrelated responses.**
  - pop3 (reproduced): assumes the third `+OK`/`-ERR` is the PASS reply; after a failed attempt consumes the banner a successful retry never reaches 3 and ends `no_response`; a CAPA reply before login shifts the count; `-ERR` to CAPA is read as auth failure.
  - redis (reproduced): `-NOAUTH` then `+OK` gives `failed`; an earlier `+OK` from SETNAME/SELECT reads as auth success.
  - ftp: stale `530`/`421`. smtp: stale `535`/`534`/`432`.
  - ldap: messageID is never compared; skipped anonymous/SASL binds leave responses in `server_buf`.
  - *Change:* offset floors for all positional protocols; correlate LDAP by messageID as snmp does by request-id. Also see #2.
- [ ] **#15 telnet `_outcome` searches all of `server_buf` and never consumes** (banner case reproduced). A "Welcome to" banner before login makes a wrong password report `success`; once any failure text appears every later attempt is `failed`. *Change:* evaluate only bytes after the password was sent; drop bare "Welcome to". Telnet also consumes no buffer, so its response can resolve a second pending finding.
- [ ] **#16 The scan window never advances without a match.** Every detector scans only `buf[:N]` (2-16 KB) and consumes only on a match, so unmatched leading bytes block later credentials (IMAP with >4 KB of other commands before LOGIN; LDAP >8 KB of searches before a rebind; SNMP; http). *Change:* trim the scanned prefix, keeping a small tail for split tokens.
- [ ] **#17 Resolved findings from 7 detectors have no `ts`.** Reviewer checked rotated `results.jsonl.*.gz`: ftp, imap, ldap, pop3, redis, smb, smtp findings lack `ts`; http_basic, snmp, telnet have it. Only http sets it in `_try_resolve`. *Change:* emit `{"ts": resolved.get("ts_start", ts), **resolved}` in the resolve loop. *Why:* dashboards/watchers and any time-based analysis break on those records.
- [ ] **#18 Workers log at DEBUG** (`pipeline.py` `basicConfig(level=DEBUG)`). `parse_basic` logs a traceback per malformed packet: journal flood and CPU. *Change:* INFO by default, DEBUG behind a config flag. (`parsing/net.py` docstring previously claimed no overhead at INFO; corrected.)
- [ ] **#19 Periodic maintenance can starve** (`pipeline.py`). `if not pkt: continue` and the exception path skip `_maybe_run_periodic`; the recv timeout only fires when the link is completely idle. Control flow verified; the traffic condition (e.g. an empty `bpf_filter` with mostly unparseable traffic) is inference. *Change:* check periodic work at the top of the loop.
- [ ] **#20 update.sh stops the service before `git pull` and has no rollback** (`update.sh` ~L61-118). `set -e` means any failure leaves the pipeline stopped. `systemctl start` on Type=simple returns immediately, so "active" lines can be false, and the script exits 0 even when it prints "NOT active". *Change:* pull first, `trap` to restart, poll after start, pre-validate config. Related: #48.
- [ ] **#21 No SIGTERM handler** (`run`/`pipeline` `main()`; already noted in its docstring). `systemctl stop` skips `flush_all()`, so pending findings are lost on every restart/update. *Change:* handle SIGTERM and flush.
- [ ] **#22 http_basic framing.** (a) POST bodies are not skipped and glue onto the next request line (empty method/uri); (b) a header block or body >16 KB with no CRLFCRLF stalls the session because nothing is consumed.
- [ ] **#23 Quadratic copying/decoding on big streams.** imap decodes all of `server_buf` on every IMAP-port packet before any LOGIN (up to 4 MB, quadratic on mailbox downloads); smtp does `bytes(server_buf)` (lower impact); `_try_resolve` runs `bytes(server_buf)` per pending finding per packet for up to 45 s. *Change:* decode lazily; search from the pending finding's floor without copying.
- [ ] **#24 redis: RESP3 `HELLO <ver> AUTH user pass` not recognised.** False negative for modern clients.
- [ ] **#25 smb: first CHALLENGE in `server_buf` is used.** A re-auth on the same connection can pair a new AUTHENTICATE with a stale challenge, producing an uncrackable hash. Final status is not matched by MessageId.
- [ ] **#26 smtp: abandoned `AUTH LOGIN` anchor stays in `client_buf`.** Later bare-alphanumeric lines (message-body words) can decode as credentials; the LOGIN path lacks the empty-credential guard that PLAIN has.
- [ ] **#27 Start method assumed to be `fork`, actually `forkserver` on Python 3.14** (reproduced via `ps`). The unit comment and REBUILD said fork. Ambient capabilities still survive `execve` (inference). *Change:* pin the start method explicitly in `pipeline.py` so an interpreter upgrade cannot change it silently.

## LOW: correctness edge cases

- [ ] **#28 Capture-filter for SNMP** (`session._make_filter`, unused) emits `tcp port` for a UDP protocol; also `detectors/snmp.py` ~L372 (reviewer flagged, unverified whether live BPF is affected). Check that the live `bpf_filter` matches UDP 161. **Observed live 2026-09-30:** a real internet SNMP scan finding in `results.jsonl` (dport 161) carries `"filter": "... tcp port ... tcp port 161"`, so the filter field emitted for SNMP findings is wrong (it says tcp for a UDP protocol).
- [ ] **#29 No TCP reassembly** (`session.py`). Payloads are appended in arrival order: retransmits duplicate bytes, out-of-order segments scramble the stream, lost SPAN packets corrupt it. Documented now. A cheap seq-based dedupe would remove the retransmit case.
- [ ] **#30 telnet `_strip_iac`.** `IAC IAC` is dropped instead of yielding 0xFF (reproduced); a split IAC sequence can leak into text; backspace/DEL unhandled; the server stream is not IAC-stripped. `not user or not passwd` is unreachable.
- [ ] **#31 ftp/pop3 regexes.** `\s+` crosses CRLF and no terminating CRLF is required, so a segment split truncates the password; `\S+` truncates passwords containing spaces. The "empty capture" guards are unreachable.
- [ ] **#32 imap.** LOGIN: `\"` escapes and `{n}` literals unhandled, no CRLF requirement. A bare `DONE` matches the base64-line regex. The immediate path does not consume the tagged response (run.py does), so reused tags can match stale responses.
- [ ] **#33 smtp.** `_SMTP_VERBS` incomplete (TURN, ETRN, ATRN, BDAT, LHLO); `AUTH LOGIN <b64user>` with an initial response is not matched.
- [ ] **#34 redis.** `$-1` mis-advances the parser; incomplete vs malformed are indistinguishable; inline `AUTH` inside a SET value is a false positive; `_OK_RE`/`_ERR_RE` are unused.
- [ ] **#35 ldap.** Result code read from a single byte; bogus/oversize length stops the scan; text decoded with `replace` rather than `ignore`.
- [ ] **#36 smb.** `offset < 0` check is dead (unsigned); the 4 KB server window is tight; any `\xfeSMB` inside a payload is treated as a header.
- [ ] **#37 snmp.** Datagrams accumulate per 4-tuple, so an unanswered request pins the 2 KB window; an empty community is dropped without a debug log.
- [ ] **#38 irc.** `NS IDENTIFY`, `NICKSERV@` and SASL not covered; Atheme "You are now logged in as" not in the accept regex; bare-LF unhandled; no `logging` import.
- [ ] **#39 Implicit-TLS default ports** 993, 995, 465 can never yield plaintext creds; they only add BPF load. Also BPF `"tcp and (port ...)"` may not match 802.1Q-tagged frames (inference).
- [ ] **#40 Session internals.** `session_id` is 32 bits of SHA-1 over a monotonic time; `_evict_one` is O(n) per new flow at capacity; `_make_key` ignores protocol (TCP and UDP with the same tuple would share a session).
- [ ] **#41 Cooldown edge cases.** `claim_slot` fails open only on `open()`; a `write`/`ftruncate` error (tmpfs full) propagates into the per-packet `except` and 100 in a row exit the worker; a backwards clock step suppresses claims; the key `dst:dport:creds` collapses empty-creds findings (e.g. `ftp_anonymous`) per (dst, dport).
- [ ] **#42 Discord sink.** Unbounded thread per finding, ignores 429/non-2xx, no retry, new connection every send. Also `JSONLSink` opens its handle once and never reopens (fine with copytruncate, breaks with rename rotation); only the stdout path loops on partial writes, and stdout is unlocked.
- [ ] **#43 Config parsing gaps** (`config.py`). Numeric settings use `getint` so `timeout_seconds = 0.5` raises; an empty or garbled `[ports]` list silently falls back to defaults (a detector cannot be disabled; `80-90` is ignored); no upper bounds or non-negative check on cooldowns; `cfg.snaplen`/`cfg.expiry_interval` are re-read inside the recv loop; `snaplen` only sizes the userspace recv (no kernel truncation).
- [ ] **#44 `multiprocessing.connection.wait` relies on an implicit submodule import.** Add `import multiprocessing.connection`.

## Architecture / better ways

- [ ] **#55 Dead code and config.** `no_immediate` is never read; `[dispatcher] socket` is validated but unused (a bad value blocks startup); most `capture.py` bindings are unused and it raises at import if libpcap is missing; `Session._make_filter` has no callers; `common.detect_user_pass` is dead (and `decode_b64` does not tolerate bad padding); http_basic listed an outcome `pending` that is never emitted. *Change:* delete or wire up.
- [ ] **#56 Two copies of every response parser.** Each detector parses the response for its immediate path and `run.py` `_try_resolve` parses it again (11-branch if/elif with inconsistent output keys). `pipeline.py` already runs `_try_resolve` on all pending findings right after the detectors, so the immediate branches could just call `add_pending`. *Change:* move to `resolve.py` (`run.py` is misnamed; it holds only `_try_resolve`) with a per-detector resolver registry. This would also fix #2, #13, #14 in one place.
- [ ] **#57 Shared helpers belong in `common.py`.** `_decode_plain` is identical in smtp and imap; the BER helpers (`_parse_ber_len`, `_parse_ber_tlv`) are identical in ldap and snmp; the base-finding dict is built in ~17 places, the port gate appears 12 times, and the resolve-or-pend tail is repeated 10 times.
- [ ] **#58 One registry for protocols plus a consistency test.** Protocol lists live in several places (`detectors/__init__.py`, `capture.py` port map, config `[ports]`, `_try_resolve`, `_SERVER_PORTS`). A missing `capture.py` entry fails silently and a missing `_try_resolve` branch makes everything `no_response`. A registry table plus a test asserting every `*_creds` type has a resolve branch would catch both. The 7-step registration checklist is now in `detectors/__init__.py` as a stopgap.
- [ ] **#59 Per-detector exception isolation.** No detector catches exceptions; one raising aborts the remaining detectors for that packet, and 100 consecutive failures exit the worker. *Change:* per-detector try/except with logging in `pipeline.py`.
- [~] **#60 No automated tests** (STARTED 2026-09-30: `tests/test_detectors.py`, stdlib `unittest`, 14 tests for #1-#3; command in README; pytest not needed. Still to add: #14, #15, #30 and the other detectors.) (also recorded in the vault project summary as of 2026-07-26). pytest is not installed. The detector parsers are pure functions of bytes and are cheap to unit test; the reproduced bugs (#1, #2, #3, #15, #14, #30) are ready-made regression cases.
- [ ] **#61 Cross-detector convention drift.** Decode errors: `ignore` in ftp/pop3/imap/smtp/telnet/http vs `replace` in redis/ldap/snmp/irc/postgres/smb. `status` is a string code, int, `str(int)` or outcome text depending on the detector. Scan-limit names differ (`_MAX_CMD_SCAN`, `_MAX_SCAN`, `_MAX_SCAN_CLIENT/_SERVER`). Pick one each.
